# 🏗️ معماری فنی و نقشه راه — پلتفرم فروش بدون سرمایه

## ۱. تصمیمات معماری MVP

| موضوع | انتخاب | چرا |
|---|---|---|
| بک‌اند | Python + Flask | راه‌اندازی در چند دقیقه، مناسب تیم کوچک سال اول |
| دیتابیس | SQLite | بدون نیاز به سرور جدا؛ مهاجرت آسان به PostgreSQL |
| فرانت‌اند | HTML/CSS/JS خام (بدون فریم‌ورک) | سبک برای اینترنت ضعیف و گوشی‌های ارزان؛ RTL و موبایل‌اول |
| احراز هویت | توکن نمایشی + شماره تماس | عمدی ساده؛ مسیر مهاجرت به OTP پیامکی (اتصالات افغان‌تلکام/روشن) |
| پرداخت | فقط COD | بزرگ‌ترین چالش بازار = اعتماد؛ پرداخت هنگام تحویل + مرجوعی شفاف |

## ۲. مدل داده

```
users(id, name, phone UNIQUE, role, city, plan, seller_code UNIQUE, token)
products(id, supplier_id→users, name, category, wholesale_price, stock, status)
seller_products(id, seller_id, product_id, margin)   -- قیمت فروش = عمده + سود
orders(id, code UNIQUE, seller_id, product_id, supplier_id, qty,
       wholesale_price*, margin*, sale_unit*, delivery_fee*, total*,
       seller_earning*, supplier_share*, platform_fee*, customer_*, status)
       (* = اسنپ‌شات لحظه سفارش؛ تغییر قیمت بعدی روی سفارش قبلی اثر ندارد)
settlements(id, seller_id, amount, label, status, paid_at)
```

**قوانین کلیدی:**
- موجودی هنگام ثبت سفارش کم و هنگام لغو/مرجوعی برمی‌گردد (جلوگیری از فروش بیش از موجودی).
- سود فروشنده فقط با وضعیت `delivered` «قابل برداشت» می‌شود.
- تغییر وضعیت فقط در مسیر مجاز (`ORDER_FLOW` در `app.py`).
- پلان رایگان: سقف ۲۰ محصول (`FREE_PLAN_LIMIT`)؛ حرفه‌ای/طلایی: نامحدود.

## ۳. API (خلاصه)

- `POST /api/auth/register|login` ، `GET /api/auth/me` (هدر `X-Token`)
- `GET /api/products?q=&category=` ، `GET /api/categories`
- فروشنده: `GET /api/seller/dashboard|items|orders|settlements|share` ، `POST/PUT/DELETE /api/seller/items` ، `GET /api/seller/suggest/<id>`
- تأمین‌کننده: `GET /api/supplier/overview|products|orders` ، `POST/PUT/DELETE /api/supplier/products`
- عمومی: `GET /api/shop/<seller_code>` ، `POST /api/orders` ، `GET /api/orders/track/<code>`
- ادمین: `GET /api/admin/overview|orders|users|settlements` ، `PUT /api/admin/orders/<id>` ، `PUT /api/admin/users/<id>/plan` ، `POST /api/admin/settlements`

## ۴. نقشه راه مقیاس‌پذیری (مطابق طرح جامع)

**مرحله ۱ (فعلی — مزارشریف، ۵۰–۱۰۰ محصول، ۱۰۰ فروشنده):**
- [x] هر ۳ پنل + فروشگاه عمومی + COD + تسویه
- [ ] OTP پیامکی، آپلود عکس محصول، سبد خرید چندمحصوله
- [ ] پنل پیامکی اطلاع‌رسانی سفارش (فروشنده/مشتری/تأمین‌کننده)

**مرحله ۲ (کابل، هرات، بلخ — ۵۰۰ محصول):**
- مهاجرت SQLite → PostgreSQL؛ کش Redis برای کاتالوگ
- ماژول لجستیک: تخصیص پیک/باربری، محاسبه ارسال بین‌شهری، رهگیری
- کیف پول فروشنده + تسویه خودکار هفتگی؛ گزارش‌گیری مالی کامل
- اپ PWA (نصب روی گوشی بدون اپ‌استور) — حیاتی برای فروشندگان موبایلی

**مرحله ۳ (تمام افغانستان — ۱۰٬۰۰۰ محصول، ۵۰٬۰۰۰ فروشنده):**
- میکروسرویس‌ها (کاتالوگ، سفارش، مالی، نوتیفیکیشن) + صف پیام (RabbitMQ/Kafka)
- موتور پیشنهاد محصول و قیمت‌گذاری هوشمند واقعی (ML روی تاریخچه فروش)
- تولید خودکار متن و پوستر تبلیغاتی (همان «امکانات هوشمند آینده» طرح)
- چندانباره (انبار مزارشریف/کابل/هرات) + تخصیص هوشمند نزدیک‌ترین انبار
- ضدتقلب: امتیاز اعتماد فروشنده/مشتری، تشخیص سفارش جعلی COD

## ۵. چک‌لیست امنیتی قبل از Production

1. OTP پیامکی + محدودسازی نرخ (Rate Limit) ورود و ثبت سفارش
2. هش رمز/توکن امن، انقضای نشست، HTTPS اجباری
3. اعتبارسنجی سمت سرور برای آپلود فایل + سقف حجم
4. بکاپ روزانه دیتابیس + لاگ حسابرسی تغییرات مالی
5. تفکیک نقش‌ها در سطح دیتابیس (کاربر فقط-خوانا برای گزارش‌ها)

## ۶. برآورد نقطه سر‌به‌سری (از طرح)

۱٬۰۰۰ فروشنده × ۵ فروش/ماه = ۵٬۰۰۰ سفارش/ماه.
با میانگین سبد ۱٬۵۰۰ ؋ و کارمزد ۵٪ ≈ **۳۷۵٬۰۰۰ ؋ درآمد ماهانه پلتفرم** (بدون احتساب حاشیه ارسال و پلان‌های پولی) —
کافی برای پوشش تیم ۵نفره سال اول.
